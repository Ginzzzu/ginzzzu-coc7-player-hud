# Current development baseline: 0.33.5

- The player **Action Request** shelf is the first main navigation button, followed by Characteristics and Skills, and opens by hover on pointer devices. Category and search filtering are local DOM filters and must not trigger a HUD render. Only actions resolvable for the assigned Actor are shown.
- The CoC7 resolver prefers embedded Item `flags.CoC7.cocidFlag.id`; localized skill-name aliases are fallback only. Fast Talk maps to «Красноречие», Persuade to «Убеждение». The optional provider still registers with `ginzzzu-gm-dashboard` only through the public interaction API/hook; do not import GM Dashboard code into this module.
- Incoming GM requests are session/transient state only. Native CoC7 checks and ChatMessages remain the source of truth; do not persist duplicate roll results.
- Combat remains in the existing Combat shelf and is intentionally absent from the Action Request catalogue.
- Incoming Keeper requests make the Request dock button pulse with a bright yellow outline until the request is completed/dismissed.
- POW is now a top-strip vital beside SAN and is directly rollable there; Luck and POW are no longer duplicated in Action Request. The old characteristic-only request category is removed.
- All pointer-device shelves, including Consequences, are hover-opened. Rerenders while a shelf is open suppress the entrance animation and restore its internal scroll/focus.
- Request availability is based on successful Actor resolution, not on a minimum skill percentage: 1% skills remain valid and visible when mapped.

# HANDOFF — Ginzzzu’s CoC7 Player HUD

Текущая версия 0.33.5 снимает модульный предел 80 для стартовых навыков, уточняет состояние счётчиков распределения, предупреждает об итоге выше 100 и явно выделяет незавершённые обязательные выборы профессии над таблицей очков.

## 1. Точка продолжения

Версия **0.33.5** сохраняет существующую механику HUD, убирает собственный предел итогового стартового навыка и делает состояние распределения однозначным. Итог навыка выше 100 немедленно отмечается как предупреждение, но не становится блокирующей ошибкой. Незавершённые выборы формулы, групп и свободных навыков получают заметную плашку обязательности. Общие бюджеты, кредитный рейтинг, специализации, нулевой стартовый опыт и запрет очков создания для «Мифов Ктулху» остаются обязательными.

- Foundry VTT: **v14** (`verified: 14.365`)
- Система: **CoC7 8.15+**
- ID модуля: `ginzzzu-coc7-player-hud`
- Для мастера создания сыщика требуется активный модуль `coc-Amygdal-chest`.
- В новый чат нужно передать полный актуальный архив и при необходимости `CoC7.zip`, `coc-Amygdal-chest.zip` и исходный `module.md` с правилами.
- После этого снова выдавать пользователю только новые и изменённые файлы с сохранением структуры каталогов.

Не использовать в качестве основы промежуточные или незавершённые сборки. Базой является содержимое полного актуального архива.

- `Coc7CombinedRollService` записывает модификатор прямо в roll requisite конкретного навыка/характеристики. Штатный `CoC7ChatCombinedMessage.rollForActor()` сам вычисляет диапазон `poolModifierRange(min, max)` и бросает общий набор десятков; модуль не вычисляет отдельные результаты вручную.

- Provider для GM Dashboard публикует `combined.modifierOptions`; Dashboard возвращает непрозрачное `modifierValue`, а CoC7-provider уже преобразует его в `poolModifier` отдельно для `checks` и `selections`, сохраняя Dashboard системно-нейтральным.

## 2. Обязательные правила разработки

Основные директивы находятся в `AGENTS.md`. Критически важно продолжать соблюдать:

- только Foundry v14 API: `ApplicationV2`, `HandlebarsApplicationMixin`, `DialogV2`;
- никакого legacy `Application`, `FormApplication`, jQuery и ручной замены `innerHTML`;
- `DataModel` отдельно от UI и бизнес-логики;
- сохранять `DataModel` во флаги только через `toObject()`;
- контекст, действия, контроллеры и сервисы держать раздельно;
- не раздувать существующие файлы: новый смысловой блок — новый сфокусированный файл;
- не создавать перекрывающие CSS-каскады: менять существующее правило или переносить его, старое удалять;
- весь CSS строго под корневыми классами модуля;
- все строки интерфейса через синхронные ключи `lang/ru.json` и `lang/en.json`;
- асинхронный I/O и глобальные Hook callbacks изолировать `try/catch`;
- после каждого этапа синхронизировать `module.json`, README и CHANGELOG.

- три канала громкости в одной горизонтальной строке;
- первой в правой системной группе находится кнопка последних сообщений: по наведению она открывает правую компактную полку с десятью последними видимыми карточками чата, старыми сверху и самым новым сообщением внизу; у бросков сохраняется штатная строка названия проверки и сложности, карточки доступны только для чтения, а отдельная кнопка восстанавливает интерфейс и открывает штатный чат Foundry через API ChatLog;
- сразу после последних сообщений находится полка «Кубики»: по наведению открывается сетка 4 × 2 со свободными публичными бросками `1d3`, `1d4`, `1d6`, `1d8`, `1d10`, `1d12`, `1d20` и `1d100`; крупную область каждой кнопки занимает встроенная иконка формы кубика, снизу остаётся только подпись `dX`; для `d3` используется общая иконка кубика, для `d100` — форма `d10`; броски создаются штатным `Roll.toMessage()` от имени назначенного сыщика и эквивалентны команде `/r`;
- сразу после полки «Кубики» находится системная кнопка `?`, открывающая по наведению двухколоночную памятку игрока по основным правилам CoC7; памятка полностью локализована, доступна только для чтения и перестраивается в одну колонку на узком экране;
- после полки «Кубики» находится полка громкости с тремя каналами;
- штатное окно выбора типа проверки, сложности и дополнительных кубиков CoC7 оформляется в стиле HUD отдельным строго scoped CSS-файлом; клиентская настройка позволяет вернуть системный вид, шаблон и механика броска не подменяются;
- штатный оверлей паузы Foundry оформляется отдельным строго scoped CSS-файлом как компактная центральная плашка без системного символа, с тонкой внутренней латунной рамкой, боковыми линиями у надписи «Мгновение застыло» и заметной циклической анимацией фокуса на всё время паузы: выраженное мягкое размытие и приглушение плавно переходят в яркую полную резкость и обратно; клиентская настройка возвращает системное оформление, механика паузы не изменяется;
- аварийный возврат интерфейса `Ctrl+Shift+H`.

В версии 0.18.0 завершена интеграция штатных состояний CoC7 в HUD игрока:

### Мастер создания сыщика

В версии 0.22.0 первый шаг предлагает два штатных набора 1920-х из `coc-Amygdal-chest`:

- `i.setup.standard-1-ru` — прежние броски характеристик с действующей перестановкой внутри групп;
- `i.setup.standard-2-ru` — распределение 460 пунктов между восемью характеристиками, при этом Удача бросается отдельно.

Для распределения пунктов действуют границы 15–90, а ИНТ и РАЗМ не могут быть ниже 40. Выбранный метод и бюджет сохраняются в схеме черновика версии 6. Старые черновики автоматически считаются методом бросков. При намеренной смене набора сбрасываются несовместимые характеристики, возраст, профессия и распределения навыков, но анкета и предыстория сохраняются. Все последующие шаги, сводка Хранителя и финальная запись Actor используют общий существующий код.

Все девять шагов и итоговая запись в закреплённый Actor подтверждены пользователем. В версии 0.15.3 уточнены подписи полей именуемых навыков на шагах 6–7, а исправления финализации 0.15.2 подтверждены в Foundry:

1. **Набор создания** — игрок выбирает `Персонаж 1920-е (Бросок)` или `Персонаж 1920-е (Пункты)`.
2. **Характеристики** — для бросков сохранены отдельные броски, «Бросить оставшиеся» и перестановка внутри групп; для пунктов используется строгий пул 460 с отдельным броском Удачи.
3. **Возраст** — возрастные правила для 15–89 лет, проверки ОБР, второй бросок Удачи для 15–19, обязательные снижения и штраф MOV.
4. **Показатели** — итоговые характеристики, половина/пятая, ПЗ, РАС, ПМ, MOV, бонус урона и телосложение.
5. **Профессия** — загружается и выбирается список из двух книг; поиск и прокрутка сохраняются, выбранная карточка выделяется.
6. **Навыки профессии** — обязательные навыки, группы и свободные выборы личной специализации сыщика, специализации, формула очков, кредитный рейтинг и распределение профессионального пула; безымянные шаблоны используют контекстные подписи «Вид искусства или ремесла», «Язык», «Родной язык» и «Среда выживания».
7. **Личные интересы** — полный список навыков набора, пул `ИНТ × 2`, отдельное распределение личных очков и общий итог с профессиональными значениями.
8. **Данные сыщика** — имя, выпадающий выбор пола, место рождения, место проживания и семь необязательных полей предыстории с сохранением в черновике.
9. **Проверка** — итоговая сводка, независимая валидация и запись данных в Actor CoC7, закреплённый за игроком.

Портрет и изображение токена в мастер создания не выводятся. Финализация не изменяет изображение закреплённого Actor, текстуру и остальные настройки прототипа токена; синхронизируется только имя прототипа. Существующие поля `personalData.avatar` и `personalData.token` сохранены в `DataModel` без смены типов только для совместимости старых черновиков.

## 6. Зафиксированные правила характеристик

- Броски берутся из выбранного `setup`.
- Можно разрешить одну перестановку значений внутри каждой группы:
  - `3D6 × 5`: СИЛ, ТЕЛ, ЛОВ, ВНЕ, МОЩ — **фиолетовая группа**;
  - `(2D6 + 6) × 5`: РАЗ, ИНТ, ОБР — **синяя группа**.
- Удача не входит ни в одну группу и не переставляется.
- Перетаскивается только выпавшее числовое значение, а не название или формула характеристики.
- Переставленные карточки имеют пунктирную рамку цвета группы.
- Исходные броски и текущее назначение значений хранятся отдельно, чтобы перестановку можно было отменить.

## 7. Зафиксированная структура навыков

На этапах распределения использовать колонки:

- База;
- Личные;
- Профессия;
- Опыт;
- Итог.

Правила:

- `Опыт = 0` при создании и не редактируется;
- отметка развития навыка хранится отдельно и при создании выключена;
- итог вычисляется, а не редактируется как независимое значение;
- итог стартового навыка вычисляется как `База + Личные + Профессия` без отдельного модульного предела;
- лишние очки не теряются, а остаются нераспределёнными;
- «Мифы Ктулху» нельзя повышать обычными очками создания;
- профессиональные и личные очки хранятся раздельно, даже когда повышают один навык;
- профессиональные навыки получают штатный флаг CoC7 `skill.system.flags.occupation`.

Черновая схема уже предусмотрена в `InvestigatorDraft`; не менять типы существующих полей без миграции.

- свободные профессиональные выборы из навыков набора;

- сумма всех обязательных множителей формулы и выбор ровно одной опциональной характеристики, когда профессия его требует;
- автоматическое добавление кредитного рейтинга и предварительное распределение его минимума;
- контроль минимального и максимального кредитного рейтинга;
- отдельные значения `База / Личные / Профессия / Опыт / Итог`;
- `Опыт = 0` и вычисляемый итог `База + Личные + Профессия`;
- запрет повышения «Мифов Ктулху» обычными очками создания;
- сохранение формулы, групп, свободных выборов, специализаций и распределений во флаге черновика;
- очистка зависимых решений при смене профессии;
- повторная сверка черновика с документом профессии при открытии мастера.

Actor на промежуточных шагах не создаётся.

### Интерфейс шага в 0.11.1

- блоки выбора уменьшены и занимают ограниченную высоту;
- таблица является главным элементом страницы и прокручивается независимо;
- шапка таблицы и колонка названия навыка закреплены;

## 10. Личные интересы в 0.12.0

Реализация использует навыки выбранного `setup` из «Сундука» и уже сохранённые профессиональные строки. Поддержаны:

- личный пул, равный итоговому значению ИНТ после возрастных корректировок, умноженному на 2;
- полный список из 40 навыков набора `Персонаж 1920-е (Бросок)`;
- единая таблица `База / Личные / Профессия / Опыт / Итог`;
- редактирование только колонки «Личные»; профессиональные очки показываются как зафиксированные значения;
- `Опыт = 0` и вычисляемый итог `База + Личные + Профессия`;
- точное распределение всего личного пула перед переходом дальше;
- предел итогового значения 80 без потери лишних очков;
- запрет повышения «Мифов Ктулху»;
- соблюдение диапазона кредитного рейтинга;
- ввод специализации для навыка набора с `requiresname`, когда в него вложены личные очки;
- сохранение личных очков и специализаций в существующем массиве `skills` черновика без изменения типов схемы;
- повторный расчёт баз и личного пула после изменения характеристик или возраста;
- сохранение совместимых личных очков при смене профессии и очистка только старых профессиональных значений;
- тот же принятый пользователем table-first стиль: крупный счётчик `Очки: потрачено / всего`, закреплённая шапка и первая колонка, компактная формула и мелкая служебная подпись.

Actor на этом этапе не создаётся.

## 11. Данные сыщика и предыстория в 0.14.0

Реализация использует уже предусмотренные в `InvestigatorDraft` объекты `personalData` и `backstory`. Типы существующих полей не менялись. Поддержаны:

- отдельный шаг «Предыстория» удалён из порядка и навигации; мастер теперь состоит из 9 шагов;
- старый черновик, остановленный на `backstory`, безопасно открывается на `personalData`;
- имя сыщика;
- локализованный выпадающий список пола: мужской, женский, другой;
- нормализация известных старых текстовых значений пола без сброса черновика;
- место рождения и место проживания;
- семь необязательных полей: описание персонажа, идеология и убеждения, значимые люди, значимые места, дорогие сердцу вещи, черты характера, травмы и шрамы;
- сохранение каждого изменения в пользовательском флаге черновика через сериализованный `DataModel`;
- изменение предыстории без полной перерисовки страницы, чтобы не сбрасывать прокрутку;
- ожидание очередей сохранения данных и предыстории перед переходом между шагами;
- завершение шага и переход дальше только после заполнения имени и выбора пола.

Портрет и изображение токена в мастер создания не выводятся. Существующие поля `personalData.avatar` и `personalData.token` сохранены в `DataModel` без смены типов для совместимости черновиков. При завершении мастер не изменяет изображение Actor и параметры его прототипа токена: их заранее или позднее настраивает Хранитель.

Новый Actor на этом этапе не создаётся.

## 12. Итоговая проверка и заполнение закреплённого Actor в 0.15.2

Шаг «Проверка» является сводкой, а не дополнительной формой. Он показывает:

- данные сыщика и выбранную профессию;
- итоговые характеристики, половину, пятую и возрастные корректировки;
- ПЗ, РАС, ПМ, MOV, бонус урона и телосложение;
- полную таблицу навыков `База / Личные / Профессия / Итог`;
- потраченные профессиональные и личные очки;
- только заполненные поля предыстории;
- конкретные незавершённые разделы с переходом к нужному шагу.

Финальная валидация выполняется отдельным доменным сервисом и повторяется непосредственно перед записью. Целевой Actor определяется только через `game.user.character`:

- за игроком должен быть закреплён Actor;
- Actor должен иметь тип `character` системы CoC7;
- игрок должен иметь права владельца;
- при невыполнении любого условия страница показывает конкретную причину и блокирует завершение.

Завершение использует реальные документы CoC7 из выбранного набора и профессии:

- новый Actor не создаётся;
- имя, характеристики, Удача, РАС, дневной предел потери РАС, сведения, пулы развития, денежная конфигурация набора и предыстория записываются в закреплённый Actor;
- имя прототипа токена синхронизируется с именем Actor, но изображение Actor, текстура токена и остальные параметры прототипа не изменяются;
- профессия и навыки добавляются как штатные встроенные Items;
- новые встроенные Items создаются через `CONFIG.Item.documentClass.createDocuments(..., {parent: actor})`, а не через переопределённый системой `actor.createEmbeddedDocuments`, чтобы CoC7 повторно не добавляла обязательные навыки профессии и кредитный рейтинг;
- совпадающие профессия и навыки переиспользуются и обновляются, отсутствующие создаются пакетно, а однозначные дубли удаляются пакетно;
- используемые мастером Items получают стабильные модульные идентификаторы источника и строки для безопасного повторного завершения;
- `adjustments.base`, `adjustments.personal` и `adjustments.occupation` сохраняются явно и раздельно;
- профессиональные навыки получают `system.flags.occupation`;
- специализации превращаются в именованные штатные навыки CoC7;
- единственный обязательный «Родной язык» вводится в отдельном явно подписанном поле над таблицей личных интересов и получает базу, равную итоговому ОБР; иностранные языки профессии остаются отдельными навыками;
- поддерживаются оба режима CoC7: массив `biography` и единый `backstory`.

Разрешение `ACTOR_CREATE` не требуется. Socket-запросов, ожидания ответа и подтверждения со стороны Хранителя нет. Штатный лист и штатный мастер создания CoC7 после завершения не открываются. Черновик очищается только после успешной записи Actor и встроенных Items. При ошибке сервис пытается восстановить предыдущее состояние Actor и затронутых Items, а черновик сохраняется. При загрузке мира отдельный сервис удаляет только однозначные дубли версии 0.15.1: в группе с одинаковым CoCID должен быть ровно один Item, отмеченный мастером; он сохраняется, остальные копии удаляются одним пакетным вызовом.

Версия 0.17.1 исправляет жизненный цикл кнопки панели Хранителя: отдельная группа Scene Controls используется как кратковременный запуск, после открытия окна восстанавливаются ранее выбранные контроль и инструмент, поэтому кнопка не остаётся подсвеченной и повторно открывает закрытое окно без перезагрузки.

## 13. Архитектурная карта

### HUD

- `scripts/applications/player-hud.js` — ApplicationV2 панели;
- `scripts/services/*` — Actor, навыки, бой, последствия, громкость, скрытие UI;
- `scripts/models/player-hud-preferences.js` — клиентские предпочтения;
- `templates/player-hud.hbs` — разметка панели;
- `styles/hud-*.css` — изолированные стили панели.

### Панель Хранителя

- `scripts/keeper/applications/keeper-creation-monitor.js` — тонкая оболочка ApplicationV2;
- `scripts/keeper/context/*` — подготовка вкладок, сводки черновика и прямой read-only сводки закреплённого Actor;
- `scripts/keeper/services/*` — чтение и представление снимков прогресса;
- `scripts/keeper/hooks.js` — GM-only инструмент сцены и автоматическое обновление;
- `templates/keeper/*` и `styles/keeper/*` — строго изолированный интерфейс панели.

### Создание сыщика

- `scripts/creation/applications/investigator-wizard.js` — тонкая оболочка ApplicationV2;
- `scripts/creation/models/investigator-draft.js` — версионированный черновик;
- `scripts/creation/context/*` — подготовка данных для шаблонов;
- `scripts/creation/actions/*` — пользовательские действия;
- `scripts/creation/controllers/*` — DOM-события ввода, поиска и drag-and-drop;
- `scripts/creation/services/*` — источники, броски, возраст, расчёты и сохранение;
- `templates/creation/parts/*` — оболочка мастера;
- `templates/creation/steps/*` — отдельные шаги;
- `styles/creation/*` — стили по смысловым блокам.

Продолжать это разделение. Не возвращать код в монолитный wizard-файл.

## 14. Проверка версии 0.17.2

Минимальный сценарий в Foundry v14:

1. Применить патч 0.17.2 поверх проверенной версии 0.17.1 и выполнить полную перезагрузку клиента.
2. Проверить игроков в состояниях «Не начал», «Заполняет», «Готов» и «Завершил»: статусы, текущий шаг, пулы и диагностические блоки должны соответствовать их данным.
3. Для незавершённого игрока проверить постепенную сводку из `draft`: данные, характеристики, показатели, навыки и предыстория появляются по мере прохождения шагов.
4. Завершить нового сыщика, очистить рабочий черновик штатным финалом и убедиться, что после обновления панель показывает полную сводку напрямую из Actor.
5. Проверить старого завершённого сыщика без снимка прогресса: вкладка должна иметь статус «Завершил», полные шаги, фактически распределённые профессиональные и личные очки и доступную сводку листа.
6. На копии старого листа удалить часть необязательных данных и убедиться, что панель не падает: показывает доступные разделы, корректные пустые состояния и предупреждение о частичных данных.
7. Переназначить игроку другого Actor и удалить тестовый Actor: после штатных Hooks панель должна показывать только текущее назначение, не использовать устаревший Actor и не выполнять миграционных записей.
8. Проверить оба режима предыстории CoC7 — массив `biography` и единый HTML-блок `backstory`.
9. Проверить повторное открытие панели, переключение игроков, кнопку закреплённого чарника и отсутствие ошибок в консолях игрока и Хранителя.

## 15. Следующая точка продолжения

Основной функционал панели Хранителя для нулевой сессии завершён в 0.17.2. Дальнейшие изменения определять по результатам игрового тестирования. Редактирование данных игрока из панели не добавлять без отдельного запроса.

Для нового чата использовать полный проект после применения и проверки патча 0.17.2 поверх 0.17.1, а не один patch-архив.
